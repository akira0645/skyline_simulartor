# GitHub Pages 持續卡頓調查

## 結論與證據

本次重現的持續卡頓主要在瀏覽器的場景繪製，不是部署失敗。模擬與 UI 重算也占用主執行緒，但只暫停模擬並不會停止舊版 Pixi 的持續渲染，因此暫停後仍然卡。

- 線上 `https://akira0645.github.io/skyline_simulartor/` 回應 200，Pages 使用 Actions，最近部署成功。
- 本環境單次量測 HTML 約 0.34 秒、主 JS 約 0.48 秒（772,292 bytes）。這只說明本環境當時的下載，不能代表所有人的網路。
- 在本機重建原始 `ad575b8` 正式版，主 JS 的檔名與下載的線上檔案完全相同：`index-Bsd57MLC.js`，兩者 SHA-256 都是 `b7afa3db5eeee5e5fbe02d489f6f2a9b85b5eec4cee3fc4856789af391a99362`。本機也能重現持續低畫面更新率，排除了必須經由 Pages 網路才能觸發的原因。
- 舊版大城市暫停後，10 秒採樣只有約 0.067 秒 JavaScript ScriptDuration，卻仍有約 11 秒 TaskDuration 與大量長任務；主要花費在繪圖／瀏覽器原生工作，而非居民模擬。CPU profile 也保留在此次工作區供比較。

## 已修正

1. **底圖快取**：地圖將 Kenney／城市圖集交錯使用，每個動畫幀都重送大量繪圖工作。改將可見底圖快取成一張紋理，選取與圖層分開；重畫底圖時才更新快取。依縮放限制快取解析度，使用 nearest 維持像素風。
2. **暫停／背景分頁停止渲染 ticker**：暫停時保留最後畫面，拖曳、縮放、建造與面板操作仍可明確重畫；恢復速度或回到分頁時重新啟動。
3. **畫面外車輛不建立圖形**：車輛的位置與排隊仍持續更新，只略過看不到的繪圖，避免鏡頭影響模擬。
4. **前車查詢改用格子索引**：原本每輛車掃描整批車輛，改查鄰近格子；保留方向、車道、距離及重疊時優先順序。
5. **UI 避免重複統計**：城市心情與選取地塊資料按模擬 tick／資料變更重新計算，不再跟著每次時間插值重算。UI 時鐘輪詢由 40ms 改成 100ms，模擬仍按實際經過時間推進，車輛動畫獨立。
6. 查看工具單純移動滑鼠不再重畫底圖；車流圖層重繪不再同一幀額外重畫一次人物與特效。

## 相同環境的比較

Chromium 無畫面模式、軟體 GPU（SwiftShader）、1600×900、大城市、1×，每階段採樣 10 秒；兩版依序執行，沒有同時跑測試。舊版是線上相同的正式 JS；新版包含本輪貨運、公車、買地與效能修正。

| 指標 | 舊版 | 新版 |
|---|---:|---:|
| 運行中畫面間隔中位數 | 149.9 ms | 83.4–100.0 ms（兩次） |
| 運行中畫面間隔 P95 | 300.0 ms | 299.9 ms |
| 暫停後畫面間隔中位數 | 166.7 ms | 16.7 ms |
| 暫停後 10 秒長任務數 | 64 | 0 |
| 暫停後主執行緒 TaskDuration | 11.07 s | 0.29 s |

新版另以提交的量測腳本重跑一次，中位數為 100ms；運行中典型幀間隔約減少 33–44%，顯示仍有環境與場景變動；最慢一段仍有約 300ms 尖峰，沒有宣稱已消除所有卡頓。暫停後 rAF 的 16.7ms 是瀏覽器閒置時的更新能力，不代表遊戲仍以 60 FPS 重畫。

這是雲端軟體 GPU 的相對比較，不是使用者電腦的 FPS 保證；尚未取得實際使用者瀏覽器的 profile。若大城市快轉仍卡，下一個較大的工作是將模擬搬到 Worker，並分離更細的地圖重畫失效範圍。

## 重跑

用 Node.js 22+、Chromium 與正式建置，啟動本機靜態伺服器後執行：

```sh
node tools/benchmark-browser.mjs http://localhost:4173/
```

必要時以 `CHROME_BIN` 指定瀏覽器路徑。腳本建立全新瀏覽器資料夾，載入大城市，依序測量運行與暫停，將摘要與 CPU profile 寫到忽略版控的 `work/browser-benchmark-*/`。比較版本時保持視窗、硬體、種子、倍率相同，依序執行，避免同時執行建置／測試。
